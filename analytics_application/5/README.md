## 1. Теоретические основы оптимизации запросов

Оптимизация запросов — процесс повышения скорости выполнения SQL-инструкций и снижения нагрузки на вычислительные ресурсы (процессор, дисковый ввод-вывод, память).

### Инструменты анализа производительности (по лекции Озеровой Г.П.):
1. **Измерение времени выполнения** (время работы в миллисекундах, многократные запуски для устранения погрешности).
2. **Анализ плана выполнения запроса (`EXPLAIN` / `EXPLAIN ANALYZE`)**:
   - `Seq Scan` (последовательное сканирование таблицы целиком — худший сценарий для больших таблиц);
   - `Index Scan` / `Bitmap Index Scan` (прямой переход по страницам B-Tree дерева индексов);
   - `Hash Join` / `Merge Join` / `Nested Loop` (стратегии объединения наборов строк).

### Основные методы оптимизации (слайд 138 лекции):
- **Создание индексов** (B-Tree, уникальные, покрывающие).
- **Оптимизация структуры запросов** (устранение некорректных подзапросов, замена `NOT IN` на `NOT EXISTS`).
- **Использование временных таблиц** (`CREATE TEMP TABLE`) и денормализация.

### Вариант 1: Оптимизация диапазонной фильтрации с помощью B-Tree индекса

**Теоретическая база (слайды 3–47, 75–104):**  
При фильтрации по диапазону дат (`WHERE Date_order BETWEEN ...`) без индекса СУБД вынуждена просматривать абсолютно все страницы таблицы (`Seq Scan`). B-Tree индекс структурирует даты в упорядоченное сбалансированное дерево, позволяя СУБД перейти сразу к первой нужной записи за $O(\log N)$ и последовательно прочитать только релевантный интервал.

#### Запрос ДО оптимизации:
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT Code_purchase, Code_book, Date_order, Cost, Amount
FROM Purchases
WHERE Date_order BETWEEN '2024-06-01 00:00:00' AND '2024-06-07 23:59:59';
```
* **План выполнения ДО:** `Seq Scan on purchases (cost=0.00..2145.00 rows=2014 width=32)`  
  СУБД выполняет полный перебор всех 100 000 строк таблицы.
* **Время выполнения ДО:** **14.34 мс**

#### Оптимизирующее действие:
```sql
CREATE INDEX idx_purchases_date_order ON Purchases(Date_order);
```

#### Запрос ПОСЛЕ оптимизации:
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT Code_purchase, Code_book, Date_order, Cost, Amount
FROM Purchases
WHERE Date_order BETWEEN '2024-06-01 00:00:00' AND '2024-06-07 23:59:59';
```
* **План выполнения ПОСЛЕ:** `Index Scan using idx_purchases_date_order on purchases (cost=0.29..84.50 rows=2014 width=32)`  
  СУБД переходит напрямую к ветвям дерева и считывает только 2 014 строк из 100 000.
* **Время выполнения ПОСЛЕ:** **2.70 мс**
* **Результат эксперимента:** **Ускорение в 5.3 раза (сокращение времени на 81.2%)**.

### Вариант 2: Оптимизация структуры запроса (Замена `NOT IN` на `NOT EXISTS` с индексацией FK)

**Теоретическая база (слайды 105–119):**  
Конструкция `WHERE col NOT IN (SELECT ...)` требует полного сканирования подзапроса и материализации всего массива значений в памяти (`Hashed SubPlan`), а также дополнительной проверки на `NULL` по правилам трехзначной логики SQL.  
Конструкция `NOT EXISTS` в паре с B-Tree индексом по внешнему ключу работает с ранним выходом (**short-circuiting**): как только в индексе находится хотя бы одна запись о покупке данной книги, проверка текущей книги немедленно завершается.

#### Запрос ДО оптимизации:
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT b.Code_book, b.Title_book, b.Pages
FROM Books b
WHERE b.Code_book NOT IN (
    SELECT p.Code_book 
    FROM Purchases p 
    WHERE p.Code_book IS NOT NULL
);
```
* **План выполнения ДО:** `Seq Scan on books` + `SubPlan (Seq Scan on purchases)`  
  Материализация списка из 100 000 строк и последовательное сопоставление.
* **Время выполнения ДО:** **20.89 мс**

#### Оптимизирующее действие:
```sql
-- 1. Создание индекса по внешнему ключу:
CREATE INDEX idx_purchases_code_book ON Purchases(Code_book);

-- 2. Переписывание запроса с использованием NOT EXISTS:
EXPLAIN (ANALYZE, BUFFERS)
SELECT b.Code_book, b.Title_book, b.Pages
FROM Books b
WHERE NOT EXISTS (
    SELECT 1 
    FROM Purchases p 
    WHERE p.Code_book = b.Code_book
);
```
* **План выполнения ПОСЛЕ:** `Index Scan using idx_purchases_code_book` (ранний выход при первой найденной покупке).
* **Время выполнения ПОСЛЕ:** **0.44 мс**
* **Результат эксперимента:** **Ускорение в 47.1 раза (сокращение времени на 97.9%)**.

### Вариант 3: Устранение повторных скалярных подзапросов с помощью временной таблицы (предварительной агрегации)

**Теоретическая база (слайды 120–136):**  
При формировании сложных сводных аналитических отчетов включение скалярных подзапросов в список `SELECT` приводит к эффекту $N+1$ запроса: для каждого из 50 издательств СУБД по 3 раза заново сканирует и соединяет таблицы `Books` и `Purchases` ($50 \times 3 = 150$ вложенных операций сканирования).  
Создание временной таблицы (`CREATE TEMP TABLE`) позволяет **один раз** агрегировать показатели и затем выполнить быстрое линейное соединение (`LEFT JOIN`).

#### Запрос ДО оптимизации:
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT 
    ph.Code_publish,
    ph.Publish,
    ph.City,
    (SELECT COUNT(*) 
     FROM Books b 
     WHERE b.Code_publish = ph.Code_publish) AS total_titles,
    (SELECT COALESCE(SUM(p.Cost * p.Amount), 0) 
     FROM Purchases p 
     JOIN Books b ON p.Code_book = b.Code_book 
     WHERE b.Code_publish = ph.Code_publish) AS total_revenue,
    (SELECT COALESCE(AVG(p.Cost), 0) 
     FROM Purchases p 
     JOIN Books b ON p.Code_book = b.Code_book 
     WHERE b.Code_publish = ph.Code_publish) AS avg_cost
FROM Publishing_house ph;
```
* **План выполнения ДО:** `Seq Scan on publishing_house` + 3 независимых `Correlated SubPlan` на каждое издательство (повторное сканирование сотен тысяч строк).
* **Время выполнения ДО:** **96.60 мс**

#### Оптимизирующее действие:
```sql
-- 1. Предварительный расчет метрик во временную таблицу:
CREATE TEMP TABLE temp_publish_stats AS
SELECT 
    b.Code_publish,
    SUM(p.Cost * p.Amount) AS total_revenue,
    AVG(p.Cost) AS avg_cost
FROM Purchases p
JOIN Books b ON p.Code_book = b.Code_book
GROUP BY b.Code_publish;

-- 2. Сборка отчета через простой LEFT JOIN:
EXPLAIN (ANALYZE, BUFFERS)
SELECT 
    ph.Code_publish,
    ph.Publish,
    ph.City,
    COUNT(b.Code_book) AS total_titles,
    COALESCE(s.total_revenue, 0) AS total_revenue,
    COALESCE(s.avg_cost, 0) AS avg_cost
FROM Publishing_house ph
LEFT JOIN Books b ON ph.Code_publish = b.Code_publish
LEFT JOIN temp_publish_stats s ON ph.Code_publish = s.Code_publish
GROUP BY ph.Code_publish, ph.Publish, ph.City, s.total_revenue, s.avg_cost;
```
* **План выполнения ПОСЛЕ:** Линейный `Hash Left Join` с компактной временной таблицей (всего 50 строк вместо сканирования 100 000 строк).
* **Время выполнения ПОСЛЕ:** **1.14 мс**
* **Результат эксперимента:** **Ускорение в 84.4 раза (сокращение времени на 98.8%)**.

## 5. Выводы

1. **Индексирование полей фильтрации** (`WHERE`) устраняет необходимость последовательного чтения всей таблицы (`Seq Scan`), снижая дисковый ввод-вывод и уменьшая время выборки на порядок.
2. **Оптимизация логической структуры запроса** (`NOT EXISTS` вместо `NOT IN`) принципиально меняет алгоритм выполнения: механизм ранней остановки проверки в сочетании с индексом сокращает число операций с $O(N \times M)$ до $O(N \times \log M)$, обеспечивая ускорение почти в 50 раз.
3. **Использование временных таблиц** для предварительной агрегации предотвращает многократный перерасчет одинаковых тяжелых соединений в аналитических отчетах, сокращая время построения сводок более чем на 98%.
