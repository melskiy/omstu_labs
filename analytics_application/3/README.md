## 1. Теоретические основы рекурсивных CTE

С помощью рекурсивных табличных выражений (`WITH RECURSIVE`) реализуются циклические вычисления на уровне базы данных, повторяющиеся многократно до тех пор, пока истинно условие останова.

### Архитектура рекурсивного выражения (из слайдов лекции)
```sql
WITH RECURSIVE имя_выражения (список_столбцов) AS (
    -- 1. Анкерная часть (Anchor Member):
    -- Базовый начальный запрос, формирующий нулевое приближение (начальное состояние).
    SELECT ...
    
    UNION ALL -- или UNION для автоматического отсечения дубликатов
    
    -- 2. Рекурсивная часть (Recursive Member):
    -- Запрос, который обращается к имени самого табличного выражения
    -- и производит шаг вычисления следующего уровня.
    SELECT ... FROM имя_выражения JOIN ...
    WHERE условие_продолжения_итераций
)
-- 3. Основной запрос к результату рекурсии:
SELECT ... FROM имя_выражения;
```

### Три ключевых направления применения рекурсивных CTE (по лекции Озеровой Г.П.):
1. **Обработка данных в иерархическом виде** (деревья: подчиненность сотрудников, рубрикаторы категорий, каталоги товаров).
2. **Обработка данных, представленных в виде графа** (поиск маршрутов между вершинами, расчет расстояния, поиск транзитных путей).
3. **Генерация последовательностей данных** (числовые ряды, временные интервалы, календарные сетки для устранения пропусков в аналитических отчетах).

### Пример 1: Обход иерархических структур данных (Дерево рубрик и жанров книг)

**Назначение:**  
Классический пример из лекции (слайды 21–30, аналог задачи «кто подчиняется сотруднику с `id = 3`»). В книжном деле книги группируются в многоуровневый иерархический классификатор: рубрика $\rightarrow$ подрубрика $\rightarrow$ конкретный жанр/направление.

**Постановка задачи:**  
Для раздела каталога «Компьютерная литература» (`Code_category = 3`) найти все дочерние рубрики любого уровня вложенности, рассчитать глубину вложенности (`level = 0, 1, 2...`) и построить полную цепочку навигации («хлебные крошки» `full_path`).

#### SQL-запрос (PostgreSQL):
```sql
WITH RECURSIVE CategoryHierarchy AS (
    -- Анкерная часть: выбираем корневой узел поддерева (id = 3)
    SELECT 
        Code_category,
        Category_name,
        Parent_category_id,
        0 AS level,
        Category_name::TEXT AS full_path
    FROM Book_categories
    WHERE Code_category = 3
    
    UNION ALL
    
    -- Рекурсивная часть: присоединяем дочерние категории
    SELECT 
        child.Code_category,
        child.Category_name,
        child.Parent_category_id,
        parent.level + 1 AS level,
        parent.full_path || ' -> ' || child.Category_name AS full_path
    FROM Book_categories child
    INNER JOIN CategoryHierarchy parent 
        ON child.Parent_category_id = parent.Code_category
)
SELECT 
    Code_category,
    Category_name,
    Parent_category_id,
    level,
    full_path
FROM CategoryHierarchy
ORDER BY level, Code_category;
```

#### Пошаговый разбор выполнения:
1. **Итерация 0 (Анкер):** В рекурсивную таблицу помещается запись с `Code_category = 3` («Компьютерная литература»), `level = 0`, `full_path = 'Компьютерная литература'`.
2. **Итерация 1:** Находятся записи, у которых `Parent_category_id = 3` (это «Базы данных» и «Языки программирования»), `level = 1`.
3. **Итерация 2:** Находятся потомки узлов предыдущего шага: для «Баз данных» находится «PostgreSQL», для «Языков программирования» — «Python», `level = 2`.
4. **Итерация 3:** Дочерних элементов больше нет, рекурсия завершает работу.

#### Результат выполнения:
| Code_category | Category_name | Parent_category_id | level | full_path |
| :---: | :--- | :---: | :---: | :--- |
| 3 | Компьютерная литература | 1 | 0 | Компьютерная литература |
| 7 | Базы данных | 3 | 1 | Компьютерная литература -> Базы данных |
| 8 | Языки программирования | 3 | 1 | Компьютерная литература -> Языки программирования |
| 9 | PostgreSQL | 7 | 2 | Компьютерная литература -> Базы данных -> PostgreSQL |
| 10 | Python | 8 | 2 | Компьютерная литература -> Языки программирования -> Python |

### Пример 2: Поиск путей в графе (Логистическая сеть маршрутов доставки)

**Назначение:**  
Пример из лекции (слайды 31–48, задача «в какие города можно добраться из города с `id = 2` и через какие города проходит путь»).

**Постановка задачи:**  
Центральный склад книжного интернет-магазина находится в **Москве**. Доставка в регионы осуществляется как напрямую, так и через транзитные распределительные хабы (Нижний Новгород, Екатеринбург, Омск и др.).  
Необходимо определить все достижимые города, рассчитать суммарный километраж доставки (`Total_Distance_km`), число перегрузоС (`Transit_Count`) и восстановить полный маршрут следования груза.

#### SQL-запрос (PostgreSQL):
```sql
WITH RECURSIVE DeliveryPaths AS (
    -- Анкерная часть: прямые рейсы из начального хаба 'Москва'
    SELECT 
        City_from,
        City_to,
        Distance_km,
        1 AS hops,
        City_from || ' -> ' || City_to AS full_route
    FROM Delivery_routes
    WHERE City_from = 'Москва'
    
    UNION ALL
    
    -- Рекурсивная часть: присоединяем транзитные рейсы из промежуточных городов
    SELECT 
        dp.City_from,
        r.City_to,
        dp.Distance_km + r.Distance_km AS Distance_km,
        dp.hops + 1 AS hops,
        dp.full_route || ' -> ' || r.City_to AS full_route
    FROM Delivery_routes r
    INNER JOIN DeliveryPaths dp 
        ON r.City_from = dp.City_to
    WHERE dp.hops < 5 -- Предотвращение бесконечных циклов в графе
)
SELECT 
    City_from AS Origin_City,
    City_to AS Destination_City,
    Distance_km AS Total_Distance_km,
    hops AS Transit_Count,
    full_route
FROM DeliveryPaths
ORDER BY Distance_km;
```

#### Пошаговый разбор выполнения:
1. **Анкер:** Находятся города, соединенные с Москвой напрямую: Санкт-Петербург (700 км), Нижний Новгород (420 км), Ростов-на-Дону (1100 км).
2. **Рекурсивный шаг 1:** Из Нижнего Новгорода находится маршрут в Екатеринбург (420 + 1000 = 1420 км), из Ростова-на-Дону — в Краснодар (1100 + 270 = 1370 км).
3. **Рекурсивный шаг 2:** Из Екатеринбурга находится маршрут в Омск (1420 + 650 = 2070 км).
4. **Рекурсивный шаг 3:** Из Омска находится маршрут в Новосибирск (2070 + 650 = 2720 км).

#### Результат выполнения:
| Origin_City | Destination_City | Total_Distance_km | Transit_Count | full_route |
| :--- | :--- | :---: | :---: | :--- |
| Москва | Нижний Новгород | 420 | 1 | Москва -> Нижний Новгород |
| Москва | Санкт-Петербург | 700 | 1 | Москва -> Санкт-Петербург |
| Москва | Ростов-на-Дону | 1100 | 1 | Москва -> Ростов-на-Дону |
| Москва | Краснодар | 1370 | 2 | Москва -> Ростов-на-Дону -> Краснодар |
| Москва | Екатеринбург | 1420 | 2 | Москва -> Нижний Новгород -> Екатеринбург |
| Москва | Омск | 2070 | 3 | Москва -> Нижний Новгород -> Екатеринбург -> Омск |
| Москва | Новосибирск | 2720 | 4 | Москва -> Нижний Новгород -> Екатеринбург -> Омск -> Новосибирск |

### Пример 3: Генерация последовательностей дат и анализ непрерывной выручки

**Назначение:**  
Пример из лекции (слайды 49–60, задача создания временных слотов с шагом 30 минут и последующим объединением с реальным расписанием через декартово/внешнее соединение).

**Постановка задачи:**  
В реальной таблице заказов `Purchases` продажи происходят не каждый календарный день. Если выполнить обычную группировку `GROUP BY DATE(Date_order)`, даты без покупок выпадут из выборки, что исказит график финансовой динамики.  
С помощью рекурсивного CTE сгенерировать непрерывный календарный ряд дат за первую половину марта 2024 года, объединить его с таблицей `Purchases` через `LEFT JOIN` и вывести точную посуточную выручку (с выводом `0.00` для дней без заказов).

#### SQL-запрос (PostgreSQL):
```sql
WITH RECURSIVE CalendarDates AS (
    -- Анкерная часть: начальная дата отчетного периода
    SELECT '2024-03-01'::DATE AS calendar_date
    
    UNION ALL
    
    -- Рекурсивная часть: инкремент даты на 1 календарный день вперед
    SELECT (calendar_date + INTERVAL '1 day')::DATE
    FROM CalendarDates
    WHERE calendar_date < '2024-03-12'::DATE -- Конечное условие генерации
)
SELECT 
    c.calendar_date,
    COUNT(p.Code_purchase) AS orders_count,
    COALESCE(SUM(p.Cost * p.Amount), 0.00) AS daily_revenue
FROM CalendarDates c
LEFT JOIN Purchases p 
    ON c.calendar_date = p.Date_order::DATE
GROUP BY c.calendar_date
ORDER BY c.calendar_date;
```

#### Пошаговый разбор выполнения:
1. **Анкер:** Инициализация календаря начальной датой `'2024-03-01'`.
2. **Рекурсия:** На каждой итерации прибавляется один день `+ INTERVAL '1 day'` вплоть до достижения границы `'2024-03-12'`. Формируется непрерывный виртуальный календарь из 12 дней.
3. **LEFT JOIN:** Каждая дата соединяется со всеми заказами за этот день. Если заказов не было, `p.Code_purchase` равен `NULL`, функция `COUNT(...)` возвращает `0`, а `COALESCE(SUM(...), 0.00)` заменяет неопределенное значение на ноль.
